# План исследования: orbit_wars как динамическая система

## Назначение документа

Это рабочий план для линии исследования, в которой мы рассматриваем orbit_wars как сложную динамическую систему с фазовыми переходами, и пытаемся извлечь из реплеев топ-игроков **нестандартные** структурные признаки, которые потом превратим в обучающий сигнал для агента.

Документ организован послойно. Каждая фаза имеет цель, гипотезы, артефакты, оценочные процедуры и **гейт** — условие, по которому мы решаем "идти дальше", "ревизовать текущую фазу", или "развернуться на другую ветку". Без гейтов легко закопаться в красивом, но бесполезном.

## 1. Большая картина

**Финальный результат** — агент, который играет существенно лучше базового BC, потому что обучается на признаках, отражающих структурную динамику игры, а не только локальные тактические паттерны.

**Промежуточные продукты, которые останутся ценными в любом случае**:
- Калиброванная value function на макро и структурных признаках (для offline RL, MCTS, фильтрации данных)
- Библиотека нестандартных признаков уровней 1–3 (для самой модели)
- Эмпирическая характеризация моментов решения партии (для взвешивания обучающих примеров)
- Каталог "leverage moves" — действий, которые значимо смещают исход

**Принципиальная развилка**: если на этапах 4–5 мы найдём настоящие нелинейные структурные сигнатуры — двигаемся в сторону физической интерпретации и инженерии перехода. Если нет — переключаемся в чисто прагматический режим: признаки + advantage-weighted BC + offline RL.

## 2. Сквозные принципы

### 2.1 Нетривиальность через бейзлайны

**Правило**: ни один результат не считается результатом без сравнения с тривиальным бейзлайном.

Минимальный набор бейзлайнов, обязательных в **любом** замере качества:
- `random_uniform` — равномерный случайный над разрешёнными ходами
- `nearest_weakest` — атака ближайшей слабой нейтралки
- `reinforce_weakest` — подкрепление самой угрожаемой своей планеты
- `linear_macro` — логистическая регрессия на 10 макро-фичах
- `xgb_macro` — XGBoost на тех же 10 макро-фичах

Любая метрика модели отчитывается **парой**: абсолютное значение и **lift над лучшим бейзлайном**.

### 2.2 Условные метрики на трудности

Каждое состояние получает скаляр `triviality_score` ∈ [0, 1]:
- 0 — все бейзлайны промахнулись, профи между собой расходятся → trudное состояние
- 1 — все бейзлайны согласны с профи, профи согласны между собой → тривиальное

Все основные метрики отчитываются в разбиении на квартилях по `triviality_score`. Lift в самом трудном квартиле — главная цифра.

### 2.3 Null models перед любым "открытием"

Прежде чем заявлять о найденной сигнатуре в данных, та же сигнатура считается на синтетическом null-датасете:
- **Null-A**: монотонная S-кривая на $V(t)$ с шумом
- **Null-B**: случайное блуждание $V(t)$ с поглощающими барьерами в 0 и 1
- **Null-C**: shuffled actions — те же состояния, действия перемешаны между похожими ситуациями

Сигнатура считается реальной, если она устойчиво воспроизводится на данных и **не воспроизводится** на nulls.

### 2.4 Артефакт-трекинг

Каждая фаза порождает набор артефактов. Артефакты регистрируются в `artifacts/registry.md` с: id, фаза, дата, краткое описание, метрики, гейт-решение, ссылки на код и данные. Это даёт нам возможность через месяц вспомнить, **почему** мы повернули.

### 2.5 Гейты с явными критериями

Каждая фаза заканчивается принятием решения по чек-листу:
- **Зелёный**: критерии успеха выполнены → следующая фаза
- **Жёлтый**: часть критериев на грани → довести текущую фазу за фиксированный таймбокс
- **Красный**: критерии не выполнены → разворот на альтернативную ветку, описанную в фазе

## 3. Фазы

### Фаза 0 — Инфраструктура и разметка тривиальности

**Цель**. Превратить 500 реплеев в унифицированный feature store и для каждого состояния посчитать `triviality_score`. Без этого все дальнейшие метрики будут самообманом.

**Срок**: 3–4 дня.

**Что строим**:
- Парсер реплеев → стандартизованный формат `(replay_id, step, state, action, outcome)`
- Pre-computed feature store в Parquet, индексированный по `(replay_id, step)`
- Реализация всех бейзлайнов как чистых функций `state → action_distribution`
- `triviality_score` для каждой ситуации

**Оценочные процедуры**:
- Sanity-check: распределение длин партий, action types, num planets — соответствует ли ожиданиям
- Распределение `triviality_score`. Норма — что-то напоминающее Beta-распределение, не вырожденное в дельта-функцию ни у 0, ни у 1
- Доля состояний в верхнем квартиле `triviality_score` (трудные) — ожидаем 15–30%

**Гейт**:
- ✅ Парсер обрабатывает 100% реплеев без потерь
- ✅ Distribution of `triviality_score` имеет содержательный спред (variance > 0.05)
- ✅ Хотя бы 50K состояний в "трудном" квартиле
- ❌ Если все состояния тривиальны (квартиль пустой) — значит датасет состоит из "очевидных" ситуаций и BC ничего нового не даст. Поворот: брать только late-game состояния, или искать другие реплеи.

**Артефакты**:
- `artifacts/feature_store.parquet`
- `artifacts/baselines.py`
- `artifacts/triviality_distribution.png`

### Фаза 1 — Baseline value function

**Цель**. Получить рабочий $V(s)$ на макро-фичах. Это смоук-тест всей инфраструктуры и одновременно один из главных полезных артефактов проекта.

**Срок**: 1–2 дня.

**Гипотезы**:
- H1.1: $V$ на 10 макро-фичах даст AUC ≥ 0.85 на holdout по реплеям
- H1.2: $V$ даёт значимый lift над `linear_macro` бейзлайном (≥ 0.03 AUC) — иначе не стоит усложнять
- H1.3: AUC растёт со временем партии и достигает плато ≥ 0.95 в последней четверти

**Оценочные процедуры**:
- AUC и log-loss на holdout, расщеплённом по `replay_id`
- Calibration plot (reliability diagram)
- AUC как функция нормализованного времени партии
- Сравнение со всеми бейзлайнами

**Гейт**:
- ✅ H1.1, H1.2, H1.3 — выполнены
- ⚠️ AUC < 0.85 в средней игре: возможно нужны более сильные модели или таргет шумит → перейти к Фазе 2 раньше
- ❌ Lift над `linear_macro` < 0.01 — значит макро-фичи коллапсируют в линейную комбинацию, и нелинейности нет. Поворот: переходить к структурным фичам.

### Фаза 2 — Нестандартные признаки состояния

**Цель**. Реализовать структурные признаки уровней 1–3 (см. предыдущие обсуждения): концентрация ресурсов, поле контроля, топология, race-pair матрицы, threat overhang, reachability volumes.

**Срок**: 4–6 дней.

**Гипотезы**:
- H2.1: Каждое семейство признаков добавляет ≥ 0.01 AUC к $V$ over macro-only
- H2.2: На трудном квартиле `triviality_score` суммарный lift ≥ 0.05 AUC
- H2.3: Race-pair матрица (доля темповых побед) — самая предиктивная отдельная фича среди новых

**Что строим**:
- Модуль `features/level1.py` — локальные кинематические признаки
- Модуль `features/level3_field.py` — три варианта поля контроля (Voronoi-weighted, time-to-reach, max-flow)
- Модуль `features/level3_topology.py` — связность, фронт, кривизна
- Модуль `features/level3_race.py` — race-pair матрицы, threat overhang
- Визуализатор полей: интерактивные heatmap'ы для трёх случайных партий — критично, чтобы посмотреть глазами

**Оценочные процедуры**:
- Ablation study: $V$ с разными подмножествами фич; reported по квартилям trudности
- Корреляционная матрица между новыми фичами — отфильтровать почти-дубликаты
- Feature importance из XGBoost
- Сравнение трёх вариантов поля контроля: какой даёт больший lift

**Гейт**:
- ✅ H2.1, H2.2 — выполнены: значит структурные признаки реально несут информацию
- ⚠️ H2.1 выполнено, H2.2 — нет: новые фичи помогают на тривиальных состояниях, но не на трудных. Это плохой знак: значит, мы дублируем макро. Ревизия: переопределить фичи.
- ❌ Lift в трудном квартиле < 0.01: structural features не дают сигнала. Поворот: вернуться к BC + advantage weighting, без отдельной структурной линии.

### Фаза 3 — Joint resource distribution embedding

**Цель**. Свести многомерное состояние ресурсов обоих игроков к низкоразмерному multimanifold'у и выяснить, есть ли там содержательная структура — бассейны, границы, типичные траектории.

**Срок**: 3–4 дня.

**Гипотезы**:
- H3.1: 2D или 3D embedding на features уровня 3 имеет различимые регионы с разной долей побед (variance долей побед между регионами > 0.2)
- H3.2: Большинство партий пересекают видимую границу между регионами в ≤ 2 раза за партию (иначе границы фиктивные)
- H3.3: Пересечения границ концентрированы в характерной фазе партии, а не разбросаны равномерно

**Что строим**:
- Embedding методы: UMAP, PCA, простой autoencoder (3-слойный) — обучить на статических снимках состояний
- Trajectory drawer: визуализация партий как траекторий в embedding'е, окрашенных по исходу
- Кластеризация регионов в embedding'е: HDBSCAN или GMM
- Win-rate per region — heatmap

**Оценочные процедуры**:
- Проверка стабильности embedding'а: запустить с 5 случайными seed'ами, посмотреть consistency регионов
- Cross-validate: split реплеев пополам, обучить два embedding'а — совпадает ли структура?
- Quantitative: classifier (XGBoost) на embedding coordinates → outcome. AUC ≥ 0.75 — значит структура реальная
- Сравнение с null: тот же embedding, но action sequences перемешаны — должна разрушиться

**Гейт**:
- ✅ H3.1, H3.2, H3.3 — выполнены: есть базы и переходы между ними, можем двигаться к motif mining
- ⚠️ H3.1 — да, H3.3 — нет: бассейны есть, но партии в них хаотично блуждают. Это интересно само по себе, но motif mining труднее.
- ❌ H3.1 не выполнен: embedding не нашёл структуры. Поворот: либо признаки слабые (возврат к Фазе 2), либо игра действительно не имеет явных режимов — переключиться на Фазу 6 (counterfactual leverage напрямую).

**Артефакты**:
- `artifacts/joint_embedding.pkl`
- `artifacts/embedding_visualization.html` (интерактив)
- `artifacts/region_winrates.png`
- `artifacts/embedding_stability.md`

### Фаза 4 — Phase transition signatures

**Цель**. Найти и формально верифицировать сигнатуры фазового перехода, **отдельные** от тривиальной монотонности $V(t)$.

**Срок**: 3–5 дней.

**Гипотезы**:
- H4.1: Маржинальное распределение $V$ при фиксированном нормированном времени $\tau \in [0.4, 0.7]$ — бимодальное (dip test p < 0.01)
- H4.2: Автокорреляция $V$ в окне перед $\arg\max |\dot{V}|$ систематически выше, чем в окне после (critical slowing down)
- H4.3: В Null-A и Null-B сигнатуры H4.1, H4.2 **не воспроизводятся**
- H4.4: Энтропия действий проигравшего падает в окне перед фазовым переходом значимо быстрее, чем у победителя

**Что строим**:
- Анализатор $V$-траекторий: $V(t)$, $\dot{V}(t)$, автокорреляции, бимодальность по окнам
- Генератор null-датасетов (A, B, C)
- Pipeline для статистических тестов с поправкой Bonferroni
- Анализатор action entropy per player per window

**Оценочные процедуры**:
- Dip test для H4.1 на 20 окнах, поправка на множественные тесты
- Тест на различие автокорреляций (Welch t-test) перед и после $\arg\max |\dot{V}|$
- Те же тесты на null-датасетах — должны не показать значимости
- Effect size для всех найденных сигнатур (не только p-values)

**Гейт**:
- ✅ H4.1, H4.2, H4.3 (особенно последний — отсутствие на nulls) — выполнены. У игры есть **настоящий** фазовый переход.
- ⚠️ Сигнатуры есть, но слабее, чем хотелось: размазанный переход, а не резкий. Это всё ещё полезно для filtering данных, но не для физических интерпретаций.
- ❌ Сигнатуры воспроизводятся на nulls: то, что мы видели, было артефактом. **Перейти к Фазе 6 без претензии на phase transition.** Это нормальный исход, не катастрофа.

**Артефакты**:
- `artifacts/transition_signatures.md` — подробный отчёт по каждой гипотезе
- `artifacts/null_comparison.md`
- `artifacts/decisiveness_curves/` — графики по выборке партий

### Фаза 5 — Motif mining и инженерия перехода

**Цель**. Найти **повторяющиеся последовательности действий и состояний**, которые предшествуют пересечению границы бассейна (Фаза 3) или фазовому переходу (Фаза 4). Описать **рецепты**, как профи строят переход.

**Срок**: 5–7 дней. Самая дорогая фаза.

**Гипотезы**:
- H5.1: Существует ≥ 3 повторяющихся motif'а длины 5–15 ходов, которые статистически чаще предшествуют выигрышному пересечению границы, чем случайные подпоследовательности
- H5.2: Motif'ы стабильны к подвыборке реплеев (Jaccard similarity между motif sets двух половин датасета ≥ 0.5)
- H5.3: Контекст противника во время motif'а имеет неслучайную структуру (например, противник в специфическом regime концентрации)

**Что строим**:
- Дискретизатор feature-trajectories в последовательности токенов (квантизация embedding'а Фазы 3 или признаков Фазы 2)
- Algorithm для motif mining: SAX + sliding window или Matrix Profile
- Statistical filter с false-discovery контролем (BH procedure)
- Анализатор контекста противника во время motif'а

**Оценочные процедуры**:
- Motif support и confidence на full vs random sub-samples
- Cross-validate motif set между независимыми подвыборками реплеев
- Comparison: те же motif'ы у проигравшей стороны — должны встречаться значимо реже
- Interpretability: для top-5 motif'ов — нарисовать "рассказ" что происходит на карте, посмотреть глазами

**Гейт**:
- ✅ H5.1, H5.2, H5.3 — есть устойчивые рецепты. Готовы интегрировать.
- ⚠️ Motif'ы есть, но размытые (низкий confidence). Использовать как soft labels, не как hard rules.
- ❌ Никаких устойчивых motif'ов: профи не имеют общих рецептов, скилл лежит в чём-то менее структурном (например, в индивидуальной точности оценки конкретных позиций). Поворот: Фаза 6 как основной выход.

**Артефакты**:
- `artifacts/motifs/` — каталог найденных motif'ов с метриками
- `artifacts/motif_stories.md` — narrative описания top-5
- `artifacts/motif_opponent_context.md`

### Фаза 6 — Counterfactual leverage

**Цель**. Оценить **причинный** вклад каждого хода в исход — насколько важен был именно этот ход, а не сопутствующие условия. Параллельная фаза, может идти вместе с Фазой 5.

**Срок**: 4–6 дней.

**Гипотезы**:
- H6.1: Распределение $\Delta V$ профи-ходов значимо смещено вправо относительно $\Delta V$ no-op (Mann-Whitney, p < 0.001)
- H6.2: Топ-10% ходов по $\Delta V$ концентрированы во времени около моментов перехода (Фаза 4) — корреляция ≥ 0.3
- H6.3: На трудных состояниях разница в $E[\Delta V]$ между топ-игроками и обычными игроками значимо больше, чем на тривиальных (interaction effect)

**Что строим**:
- Counterfactual estimator: для каждого хода — оценка $V$ после no-op альтернативы и после случайной альтернативы из набора legal moves
- Если есть/можем написать симулятор — полные K-шаговые rollout'ы для top-ходов
- Importance sampling estimator на k-NN в feature space, как fallback без симулятора

**Оценочные процедуры**:
- Bootstrap confidence intervals для $E[\Delta V]$ по разным методам
- Sensitivity analysis: насколько $\Delta V$ меняется при разных $V$-моделях (Фаза 1, Фаза 2)
- Validation: для тех ходов, где есть симулятор-rollout, — насколько IS estimate близок к truth

**Гейт**:
- ✅ H6.1, H6.2, H6.3 — выполнены. Leverage — рабочая мера качества хода, можем использовать как loss weights.
- ⚠️ H6.1 — да, H6.3 — нет: профи отличаются в среднем, но не на трудных моментах больше. Это слабый признак скилла как такового.
- ❌ Распределения $\Delta V$ профи и альтернатив не отличаются: либо метрика плохая (поверить trust в симулятор-вариант), либо реальный сигнал не в этом. Возврат к структурным признакам как основному пути.

**Артефакты**:
- `artifacts/leverage_estimates.parquet`
- `artifacts/leverage_validation.md`
- `artifacts/top_leverage_moves.html` — каталог самых "плечевых" ходов с визуализацией

### Фаза 7 — Интеграция в агента

**Цель**. Использовать всё накопленное (признаки, value, motif'ы, leverage) для обучения агента, который значимо лучше baseline BC.

**Срок**: 5–7 дней + цикл итераций.

**Что делаем**:
- Базовая BC модель + новые признаки (Фаза 2, 3) как вход
- Loss weighting через `triviality_score` (downweight тривиальных) и `leverage` (upweight плечевых)
- Optionally: советники-эксперты по архетипам из Фазы 3 + gating
- Optionally: offline RL (AWAC) на основе $V$ из Фазы 1+2 как critic

**Оценочные процедуры — главное**:
- **Round-robin tournament** против бейзлайн-эвристик: random, nearest_weakest, плюс публичные простые боты если доступны
- **Self-play tournament**: новые версии модели vs предыдущие
- ELO rating каждой версии
- Conditional accuracy: BC accuracy на трудных состояниях
- A/B между вариантами: weighted vs unweighted loss, с/без motif features

**Гейт интеграции**:
- ✅ Финальная модель показывает значимый ELO lift против лучшего бейзлайна (≥ 100 ELO) и conditional accuracy на трудных квартилях ≥ +0.05 vs Phase 1 baseline
- ⚠️ ELO lift есть, но малый: продолжать итерации, искать что недокручено
- ❌ Lift отсутствует: жёсткая ретроспектива — что мы упустили, имеет смысл переключаться на self-play RL с симулятором

**Артефакты**:
- `artifacts/agent_v3.onnx` (или эквивалент)
- `artifacts/tournament_results.md`
- `artifacts/elo_history.csv`

## 4. Дерево решений

Ключевые поворотные точки. Стрелка `→` означает "перейти к фазе".

```
Phase 0 ─┬─ ✅ → Phase 1
         └─ ❌ (нет trudных состояний) → переосмыслить датасет

Phase 1 ─┬─ ✅ → Phase 2
         └─ ❌ (нет lift над линейкой) → сразу Phase 2 с большей amped

Phase 2 ─┬─ ✅ → Phase 3
         ├─ ⚠️ (помогает на лёгких, не на трудных) → переопределить признаки
         └─ ❌ (нет lift на трудных) → пропустить 3-5, перейти к 6 + 7

Phase 3 ─┬─ ✅ → Phase 4 + 5
         ├─ ⚠️ (бассейны без переходов) → Phase 4, пропустить 5
         └─ ❌ (нет структуры) → пропустить 4-5, к Phase 6

Phase 4 ─┬─ ✅ → Phase 5 уверенно
         ├─ ⚠️ (слабый переход) → Phase 5 с осторожностью
         └─ ❌ (артефакт null) → пропустить 5, к Phase 6

Phase 5 ─┬─ ✅ → motif'ы в Phase 7
         ├─ ⚠️ → motif'ы как soft signal
         └─ ❌ → Phase 7 без motif'ов

Phase 6 — параллельно. Её результат идёт в Phase 7 как loss weights независимо.

Phase 7 ─┬─ ✅ финальный агент готов
         ├─ ⚠️ итерации
         └─ ❌ ретроспектива + рассмотреть self-play RL
```

## 5. Реестр рисков

Сводка failure modes с индикаторами, которые их выдадут раньше, чем мы потратим много времени.

| Риск | Индикатор | Реакция |
|------|-----------|---------|
| BC потолок упирается раньше, чем мы доберёмся до Phase 7 | Phase 2 lift в трудном квартиле близок к нулю | Перейти к offline RL раньше, не доводя структурную линию |
| "Найдено" в Phase 4 — артефакт | Сигнатуры воспроизводятся на null-датасетах | Откатить заявление, пропустить Phase 5 |
| Motif mining даёт сотни нестабильных motif'ов | Cross-validation Jaccard < 0.3 | Усилить статистический фильтр или отказаться от motif'ов |
| Поле контроля плохо определено | Glaz-проверка показывает странные heatmap'ы; три варианта поля дают разные lift'ы | Вернуться к определению поля; держать только один работающий вариант |
| Endogeneity макро-фич | Coefficients XGB указывают на "production_diff" как главный, но при стратификации эффект исчезает | Сместить фокус на momentum/dynamical features |
| Counterfactual без симулятора нестабилен | $\Delta V$ оценки сильно зависят от $V$-модели | Написать минимальный симулятор для 50 партий, валидировать IS |
| Победили в датасете в основном агрессивные стили | $V$ полагается на агрессивные признаки, проигрывает турелям | Стратифицировать по стилю в Phase 3, обучать conditional |
| Метрики хорошие, ELO нет | Phase 7: модель точна, но проигрывает в боях | Симулятор + self-play, BC потолок |

## Заметки на полях

- **Объём работ**: при сосредоточенной работе одного человека — 5–7 недель до конца Phase 7. С параллелизацией Phase 5 и 6 — на 1–2 недели быстрее.
- **Минимальный полезный итог** (если бросить после Phase 2): сильный value function и набор структурных признаков, которые сами по себе улучшат BC. Это уже окупает Phase 0–2.
- **Что должно остаться в репозитории** независимо от исхода: feature library (Phase 2), value function (Phase 1+2), baseline harness и triviality scoring (Phase 0). Это переиспользуемая инфраструктура для любой будущей линии.
- **Симулятор**: я несколько раз упоминал "если есть симулятор". Если правила игры известны и стабильны, имеет смысл **на старте Phase 0** заложить день-два на минимальный симулятор. Он окупится в Phase 5, 6, 7 многократно. Если правила Kaggle нетривиально сложны — оставить как условный пункт для Phase 6.
